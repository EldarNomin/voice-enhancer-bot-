# MAX + Telegram

Оба канала используют PostgreSQL, Redis, один media worker и одинаковые пресеты.
GLM остаётся необязательным переводчиком текстовых пожеланий в параметры; оплата
GLM не нужна для получения файла, выбора пресета и обработки звука.

## Что реализовано

- Официальный HTTP API MAX, актуальный адрес `https://platform-api2.max.ru`.
- `/start`, аудио/голосовые, видео, поддерживаемые аудио/видеофайлы во вложениях.
- Natural / Studio / Reels / Podcast, прогресс, результат, «Другой стиль», новый файл.
- `/delete_my_data`: история, файлы и отложенные повторы старых MAX-событий.
- Отдельные пространства пользователей и сообщений: одинаковые числовые user ID
  в Telegram и MAX не означают одного владельца. MAX `mid` сохраняется строкой.
- Секрет webhook, ограничение тела 1 MiB, PostgreSQL inbox до HTTP 200,
  дедупликация, 5 попыток обработки, восстановление после остановки ingress.
- Удаление payload inbox после обработки; ключ дедупликации живёт 7 суток.
- Асинхронная готовность медиа MAX: повтор отправки `attachment.not.ready` с паузой.
- Потоковое скачивание с ограничением размера и проверкой каждого CDN redirect.
  Токен бота передаётся только API, не CDN. TLS-проверка обязательна.

В этой версии принимается один медиафайл из сообщения, до 250 MiB и 10 минут.
Для сохранения максимального качества видео скачивается по `/videos/{token}`,
выбирается наибольшее доступное MP4-разрешение. Уже выполненную MAX перекодировку
бот не может отменить; для оригинала стоит отправлять видео как файл.

## Запуск обоих каналов

1. Создать и верифицировать бота через MAX для бизнеса, получить токен. По текущей
   официальной схеме регистрация доступна юрлицам, ИП и самозанятым резидентам РФ.
2. Заполнить обычные Telegram-параметры и `MAX_BOT_TOKEN` в `.env`.
3. Сгенерировать `MAX_WEBHOOK_SECRET`, например `python -c 'import secrets;
   print(secrets.token_urlsafe(32))'`. Сохранить в `.env`, не в git.
4. `docker compose --profile max up -d --build`.
5. Опубликовать только API через HTTPS reverse proxy на 443. Например Caddy на
   хосте: `bot.example.ru { reverse_proxy 127.0.0.1:8080 }` (заменить домен).
6. Проверить доступ: `docker compose exec api python scripts/configure_max.py`.
7. Зарегистрировать: `docker compose exec api python scripts/configure_max.py
   --webhook https://bot.example.ru/webhooks/max`.

Полный пример регистрации — одной строкой в терминале, переносы выше только для
читабельности. MAX webhook требует доверенный TLS-сертификат; self-signed не подходит.
Long polling одновременно с активной подпиской не работает и здесь не используется.

## Только MAX

Compose >= 2.24.4:

```sh
docker compose -f docker-compose.yml -f compose.max-only.yml --profile max up -d --build
```

В этом режиме Telegram-сервисы не запускаются и Telegram credentials не нужны.
Нельзя отключать канал при незавершённых заданиях этого канала в общей БД.
Для локального AI добавить `-f compose.deepfilter.yml` или `-f compose.gtcrn.yml`
перед `--profile max`. Выбрать один override; GTCRN выдаёт моно 16 кГц до DSP.

## Сертификаты и CDN

Документация MAX требует доверия к сертификату Минцифры. При необходимости
администратор получает и проверяет официальный сертификат и добавляет его в PEM
bundle. Этот bundle монтируется read-only в worker и max-ingress, путь указывается
в `MAX_CA_BUNDLE`. Он должен включать и обычные публичные CA для CDN.
Нельзя использовать `verify=False` или выключать TLS-проверку глобально.

`MAX_MEDIA_HOSTS` — разрешённые домены CDN и их поддомены. Значения по умолчанию
покрывают max.ru, okcdn.ru, mycdn.me, userapi.com. Если живой API возвращает другой
официальный CDN, его необходимо проверить и добавить явно. Не добавлять `*`.
Без токена список фактических CDN этого бота проверить невозможно.

## Проверки и пределы готовности

Автотесты проверяют официальный формат HTTP запросов и ответов, секрет webhook,
устойчивость inbox, отсутствие ACK при ошибке БД, сохранение строковых ID,
изоляцию владельцев, скачивание, upload token и отложенную готовность медиа.
Есть проход «событие MAX → пресет → общий worker → результат → повтор → удаление»
с подменённым MAX API; FFmpeg и DeepFilterNet проверяются отдельными реальными тестами.
Это не live-проверка MAX. Для неё нужны токен, домен с HTTPS и доступный сервер.

Остаётся ограничение at-least-once доставки результата: если процесс упал после
успешного POST /messages, но до фиксации результата в БД, возможен повторный ответ.
API отправки сообщений не даёт idempotency key. Заявлять exactly-once доставку нельзя.
Ingress и обработчик рассчитаны на один экземпляр каждого с общим volume; lock
защищает восстановление очереди. Для нескольких узлов нужны leases и object storage.

При длительной недоступности webhook MAX может автоматически снять подписку;
мониторинг должен проверять `/subscriptions` и состояние failed inbox.
Ошибки inbox логируются только по ID/типу, без подписанных медиа-URL.
