# Windows: проверка и запуск

Работаем через Linux-контейнеры Docker Desktop, не нативный Python на Windows.
Локальные GTCRN и DeepFilterNet сейчас используют CPU: RTX 4070 не нужна для
первого запуска. Производительность на конкретном ПК ещё необходимо измерить.

## Подготовка

Установить Docker Desktop с WSL 2 по [официальной инструкции](https://docs.docker.com/desktop/setup/install/windows-install/).
Включить Linux containers и запустить Docker Desktop. Нужен Compose >= 2.24.4
из-за `!override` в MAX-only конфигурации ([документация](https://docs.docker.com/reference/compose-file/merge/)).
Скрипт сам не устанавливает программы, не меняет Execution Policy, брандмауэр
или настройки сна. Не отправляйте содержимое `.env` и вывод `docker compose config` в чат.

PowerShell, из корня репозитория:

```powershell
.\scripts\windows.ps1 -Action Check
.\scripts\windows.ps1 -Action Init
```

`Init` создаёт `.env` только при отсутствии файла. Заполнить ключи вручную позже.
Если корпоративная политика запрещает скрипты, не обходить её: использовать
разрешённый личный ПК или согласовать запуск с администратором.

## Проверка без Telegram, MAX и платежей

```powershell
.\scripts\windows.ps1 -Action Offline -Provider gtcrn -InputFile 'C:\Audio\speech.wav' -OutputFile 'C:\Audio\result.m4a'
```

Для видео выход `.mp4`, для аудио `.m4a`. Выходной каталог должен существовать,
выходного файла ещё не должно быть. Пути с пробелами поддерживаются, с запятыми
не поддерживаются. Относительные пути считаются от корня репозитория.
Варианты `-Provider ffmpeg`, `deepfilter`, `gtcrn`; пресеты `-Preset natural`,
`studio`, `reels`, `podcast`. Первая сборка скачивает зависимости и модель.
Сам контейнер обработки запускается без сети и без `.env`; исходник монтируется
только для чтения. Не требует PostgreSQL, Redis, токенов и платных API.

## Подключение каналов позже

```powershell
.\scripts\windows.ps1 -Action Start -Channel telegram -Provider gtcrn
.\scripts\windows.ps1 -Action Status -Channel telegram -Provider gtcrn
.\scripts\windows.ps1 -Action Stop -Channel telegram -Provider gtcrn
```

Использовать одинаковые Channel/Provider при Start/Status/Stop.
Для MAX: `-Channel max`, для обоих: `-Channel both`. MAX дополнительно требует
публичного HTTPS webhook и регистрации подписки: [MAX.md](MAX.md).
Скрипт не открывает порт в интернет и не регистрирует webhook автоматически.
Для `-Provider ffmpeg` значение ENHANCEMENT_PROVIDER в `.env` должно быть ffmpeg;
AI override-файлы выставляют выбранного провайдера сами.

`Stop` сохраняет тома, задания и файлы. Сон/выключение ПК останавливает доступность
бота. После возврата Docker/worker восстанавливают очередь, но доставку конкретного
сообщения следует проверить. VPS не нужен для офлайн-проверки.

## Безопасная диагностика

`Status` показывает доступность БД/Redis, количество заданий по статусам, длину
очереди, heartbeat worker и свободное место. Нет ID пользователей, имён файлов,
текстов сообщений, токенов и URL подключений. Код выхода 1 означает «не готов».
Heartbeat означает живой event loop, а не успешность внешней доставки; начатое
задание всё ещё может завершиться ошибкой. MAX ingress/webhook отдельно проверить
реальным сообщением после подключения.

По умолчанию: 3 незавершённых задания на пользователя **в каждом канале**, 100
на весь бот, 2 параллельных скачивания на хост, одно на пользователя. CREATED
(ожидает выбора пресета) тоже занимает квоту. Идентичные числовые ID в двух
мессенджерах не считаются одним человеком. Ограничения задаются в `.env`.

Диск: сохраняется запас MIN_FREE_DISK_BYTES (1 GiB), место для результата размером
до MAX_MEDIA_SIZE_BYTES и трёх stereo float32 PCM буферов. До скачивания дополнительно
резервируется MAX_CONCURRENT_UPLOADS × MAX_MEDIA_SIZE_BYTES (одинаково для каналов).
Это консервативная проверка, не файловая квота: сторонние программы могут заполнить
диск после неё. Worker при низком запасе ждёт, не списывая попытки; очистка TTL
продолжается. Docker VM должна иметь достаточно свободного места внутри своего диска.

Модель рассчитана на **один хост и общий media volume**. Перед горизонтальным
масштабированием файловые lock-и и single-worker архитектуру надо заменить.
